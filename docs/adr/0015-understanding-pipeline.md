# Understanding: a validator that guarantees the Walkthrough, Scope from a confirmed Intent, and OpenAI behind the same router

M3 builds the Intent, the Walkthrough, Scope and Risk, and the Change Brief (engineering plan §9.1–9.3), adds the Judge (ADR 0005) and the OpenAI runtime (ADR 0006). The main process runs the stages (`apps/desktop/src/main/understanding.ts`), the agent host runs every model call and judgment, and the indexer computes the Fragment graph. These are the decisions made while building it.

**The model proposes; a deterministic validator decides.** The planner (mid tier) groups Fragments into Steps under short aliases (`F1`, `F2`…) and proposes an order. `assembleWalkthrough` then guarantees the properties the exit criteria name, whatever the model said: every Fragment in exactly one Step (unknown aliases dropped, duplicates kept first, left-out Fragments planned once more and then put in an "Other changes" Step), tests moved into the Step of the code they test, and an order in which no Step uses what a later Step changes. Ordering is a stable topological sort over strongly connected components, with the model's order as priority, so mutual recursion stays together and is counted as a cycle rather than a violation. Chapters are the model's feature names, used only when there are two or more; Chapters that depend on each other both ways are merged, since they aren't independent. A randomized test runs 200 arbitrary planner outputs through it. If no model can plan, a Walkthrough by file is built instead, so the app keeps working without a provider.

**Dependencies come from the code index, not the model.** `CodeIndex.fragmentGraph` says which changed Symbols each Fragment touches (the innermost ones, plus containers whose declaration it touches) and draws an edge from Fragment A to Fragment B when a Connection site inside B resolves to a Symbol A changes. Only resolved and "likely" Connections count, on Head. Blast radius is the count of Symbols reaching a changed one within three hops of Used by. Tests link to the Fragments they use, else to the file they're named after.

**Step ids are a hash of their Fragment ids.** A Step whose Fragments are all unchanged on a new Iteration keeps its id, name, narrative, edits and viewed mark; only the remaining Fragments are planned again. Steps hold their Fragments' line ranges, so the viewer finds a Step's chunks whether or not whitespace changes are hidden.

**Scope waits for a confirmed Intent.** An Inferred Intent describes what the code does, so every Step would look Requested. Scope is judged only once the Intent came from a source (the Pull Request, linked issues, Agent Transcripts) or the user confirmed or edited it. Risk doesn't wait.

**One Judge request per stage.** Scope (`step-scope`), requirement coverage (`requirement-covered`) and Risk signals (`risk-signal`, only for areas the detectors found) share one request over the same evidence: the Intent, then each Step's name, narrative, files and changed Symbol names. No code is sent to a Judge. Answers below their threshold show as "likely", or fall back to the detector's word for Risk. Thresholds start at 0.7 for TypeSafe and OpenAI Decisions and 0.8 for the fast tier, whose self-reported confidence runs high, until Judge evals tune them. A failing external backend falls back to the fast tier and says why.

**Risk is detectors, confirmation and reach.** Detectors look for auth, payments, crypto, migrations, deletes, concurrency and public API changes in paths, Symbol names and changed lines. A public API change is a removed or changed exported declaration, or a route. One of auth, payments, crypto or migrations is elevated; a second of those, or wide reach (5 callers or 20 Symbols within three hops), makes it critical. Deletes, concurrency and public API changes are elevated only with wide reach, and very wide reach (15 callers or 60 Symbols) is elevated on its own. The plan's model adjustment with a stated reason isn't built.

**One spend cap per Iteration's build** (Settings → Spend, $2 by default), shared by every run in it. Each run is recorded in `agent_runs` with the provider, model and tier that actually ran it. Planner outputs are cached by prompt, provider, model and prompt version.

**The OpenAI runtime meters every model call itself.** `OpenAIAgentsRuntime` wraps the Agents SDK's model in one that refuses a request when spend so far plus the request's estimated input would pass the cap, and prices usage from the catalog. Tools are Legible's function tools in strict mode; there are no hosted tools. SDK tracing is turned off, so nothing about a run leaves the machine but the model request. `openai` is pinned to a release at least two weeks old.

**"Continue with ChatGPT" needs a registered client id.** The OIDC + PKCE flow with a loopback redirect is built, and tokens go to the keychain under a name the renderer can't write. Builds without `MAIN_VITE_CHATGPT_CLIENT_ID` offer only an API key and say why. The issuer, API base and redirect port are build settings, because the program's exact values come with the registration.

**Stored as JSON documents.** Intents, Walkthroughs and Briefs are one JSON row each (`intents`, `walkthroughs`, `briefs`), not the plan's normalized `steps`/`step_fragments` tables. Steps are always read and written whole, and edits re-validate the whole Walkthrough. Viewed Steps have their own table, keyed by Step id.

## Consequences

- The exit criteria that depend only on the validator, 100% coverage and 0 dependency violations, are checked on every labeled case in `pnpm test`. Unrequested recall and Domain Change quality need live eval runs (`evals/README.md`).
- OpenAI models stay `experimental` in the catalog until a live eval passes them for a tier.
- Agent Transcripts are read only from sessions whose folder is the repository or one of its worktrees, during the window of the change, and only when Settings → Walkthrough & Brief allows it. Pull Request Reviews (cached clones) have no local folder, so they get no transcripts.
- Updating the Pull Request description and drafting a Note about a Description Gap need host writes, which arrive in M4. The Brief offers the suggested wording to copy.
